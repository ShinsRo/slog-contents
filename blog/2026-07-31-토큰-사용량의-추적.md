일일, 일주일 그리고 한 달 동안 토큰을 얼마나 사용했을까? 측정과 진단은 모든 개선의 초석이라고 생각하지만, 정작 내 자신의 토큰 사용량을 기록하지 않고 있음을 깨달았다. 하여 이번 글은 토큰 사용량 추적을 위한 n 가지 도구와 그에 따른 방법을 정리한다.

## CLI 를 통한 기본 명령어: `/usage`

가장 먼저 손이 가는 것은 클로드 코드에 내장된 `/usage` 다. (예전의 `/cost` 는 이 명령으로 흡수되었다.)

화면은 크게 두 부분으로 나뉜다. 상단의 Session 블록은 **현재 세션**의 모델별 토큰 수(input / output / cache read / cache write)와 그로부터 계산한 비용 추정치를 보여준다.

```text
Total cost:            $0.55
Total duration (API):  6m 20s
Total duration (wall): 6h 33m 10s
Usage by model:
   claude-sonnet-4-6:  1.2k input, 5.3k output, 940.0k cache read, 50.0k cache write ($0.55)
```

하단은 구독 플랜(Pro / Max / Team / Enterprise) 사용자에게만 보이는 플랜 사용량 영역이다. 5시간 세션 창과 주간 창의 소진율을 막대로 표시하고, `d` / `w` 키로 최근 24시간과 7일을 오갈 수 있다. 최근 사용량을 스킬·서브에이전트·플러그인·MCP 서버별 비중으로 쪼개 보여주고, 롱 컨텍스트나 캐시 미스가 전체의 10% 이상을 차지하면 경고로 짚어준다.

문제는 여기서 **누적 이력을 볼 수 없다**는 점이다.

- Session 블록의 토큰 수는 현재 세션 한정이고, `/clear` 하면 0부터 다시 센다.
- 플랜 사용량은 "몇 % 소진"이라는 비율일 뿐, "이번 주에 몇 토큰을 썼는가"라는 절대량이 아니다.
- 집계 범위가 이 머신의 로컬 세션 히스토리라, 다른 기기나 claude.ai 쪽 사용량은 빠진다.
- 표시되는 달러 금액은 정가 기준의 로컬 계산값이라 실제 청구서와 다를 수 있다.

일·주·월 단위로 추이를 남기려면 별도의 도구가 필요하다. 참고로 컨텍스트 윈도우 점유율만 보고 싶다면 `/context` 가 따로 있고, 이를 상태줄에 상시 노출시킬 수도 있다.

## 오픈소스: claude-monitor

링크: [Maciek-roboblog/Claude-Code-Usage-Monitor](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor)

<!-- 이미지: ../assets/2026-07-31-토큰/1.png -->

터미널에 상주하는 **실시간 모니터**다. 5시간 세션 창을 기준으로 소진 속도(burn rate)를 계산하고, 이 속도라면 언제 한도에 걸리는지 예측해 미리 경고한다. 한도에 부딪히고 나서야 알게 되는 상황을 피하려는 것이 이 도구의 목적이다.

기본 창은 실시간 뷰지만 `--view` 로 일별·월별·세션별·burn-rate 뷰를 전환할 수 있고, `--warehouse` 를 켜면 클로드가 30일 뒤 정리해버리는 로컬 로그를 자체 DB에 계속 쌓아둔다. `--statusline` 은 클로드 코드가 내려주는 공식 `rate_limits` 값을 잡아채는 옵션으로, 이 값이 있을 때는 추정치가 아닌 공식 수치로 표시된다. 화면의 각 수치에 official / local estimate / experimental 같은 신뢰도 라벨이 붙는 점이 이 도구의 성실한 부분이다.

설치는 파이썬 패키지 매니저를 쓴다. `uv` 를 권장한다.

```bash
uv tool install claude-monitor
# 또는
pipx install claude-monitor

claude-monitor --plan max20
claude-monitor --view daily
claude-monitor --once --output json   # 상태줄이나 외부 스크립트용 단발 출력
```

`--plan` 은 `pro` / `max5` / `max20` / `team` / `custom` 을 받는다. `custom` 을 주면 과거 사용 패턴의 P90 을 분석해 한도를 스스로 잡는다.

| 장점 | 단점 |
| --- | --- |
| 한도 도달 시점을 미리 예측·경고 | 파이썬 3.9+ 런타임과 설치 과정이 필요 |
| `--warehouse` 로 30일 이후의 장기 이력 보존 | 터미널 한 칸을 계속 점유하는 상주형 |
| 공식 수치와 로컬 추정치를 라벨로 구분 | 클로드 코드 로컬 로그 전용 (커서, 클로드 데스크톱 미지원) |
| JSON / CSV 출력으로 상태줄 연동 용이 | 최초 실행 전 최소 한 번의 세션 기록이 있어야 함 |

## 오픈소스: claude-usage (웹 대시보드)

링크: [phuryn/claude-usage](https://github.com/phuryn/claude-usage)

<!-- 이미지: ../assets/2026-07-31-토큰/2.png -->

터미널이 아니라 **브라우저에서 보는 로컬 대시보드**다. `~/.claude/projects/` 의 JSONL 세션 로그를 스캔해 SQLite 에 넣고, 로컬 웹 서버(기본 8080 포트)로 차트와 표를 그려준다. 모델별·기간별 토큰 추이, 캐시 read/write 지표, 프로젝트 단위 세션 히스토리를 일별·시간별로 볼 수 있고, 날짜 범위 필터는 URL 에 반영되어 그대로 북마크할 수 있다. Pro / Max 구독자의 경우 로그에 값이 있으면 진행 바도 함께 표시된다.

설치 경로는 여러 갈래인데 맥이라면 홈브류가 가장 간단하다.

```bash
brew tap phuryn/claude-usage https://github.com/phuryn/claude-usage
brew install phuryn/claude-usage/claude-usage
claude-usage dashboard

# OS 무관
uv tool install git+https://github.com/phuryn/claude-usage
claude-usage dashboard
```

표준 라이브러리(`sqlite3`, `http.server`)만 쓰기 때문에 서드파티 의존성이 없고, `~/.claude/` 에 읽기 권한만 요구한다. 데이터가 밖으로 나가지 않는다는 점이 이 부류 도구들의 공통된 셀링 포인트다.

| 장점 | 단점 |
| --- | --- |
| 차트 기반이라 장기 추이 파악이 직관적 | 브라우저를 띄워야 하므로 즉답성은 CLI 보다 떨어짐 |
| 외부 의존성 없음, 로컬 밖으로 데이터 미전송 | 실시간 경고·예측 기능은 없음 |
| 날짜 범위 필터를 URL 로 공유·북마크 | Cowork 세션은 서버 사이드라 로그 자체가 없어 미집계 |
| 캐시 토큰까지 모델별로 분리 표시 | 구독 플랜은 정액제라 비용 수치가 실제 청구와 무관 |

## 오픈소스: ccusage

링크: [ccusage/ccusage](https://github.com/ccusage/ccusage)

<!-- 이미지: ../assets/2026-07-31-토큰/3.png -->

이 분야의 사실상 표준이다. 별 1.7만 개로 위 두 도구를 합친 것보다 많다. 로컬 JSONL 을 읽어 표로 집계한다는 원리는 같지만, 설치 없이 `npx` 한 줄로 끝나는 진입 장벽의 낮음이 결정적이다. 지금은 클로드 코드를 넘어 Codex, Copilot CLI, Gemini CLI 등 15종 이상의 코딩 에이전트를 함께 집계한다.

```bash
npx ccusage@latest daily      # 일별
npx ccusage@latest weekly     # 주별
npx ccusage@latest monthly    # 월별
npx ccusage@latest session    # 세션별
npx ccusage@latest blocks     # 5시간 과금 창 단위
```

이 글의 원래 목적, 그러니까 "기록"에 가장 잘 맞는 것도 이 도구다. JSON 으로 뽑아 파일에 쌓아두면 그대로 시계열 데이터가 된다.

```bash
npx ccusage@latest daily --json > usage-$(date +%Y%m%d).json
npx ccusage@latest monthly --breakdown          # 모델별 분해
npx ccusage@latest daily --since 20260701 --instances   # 프로젝트별 그룹
```

`--offline` 은 캐시된 가격표를 써서 네트워크 없이 계산하고, `--no-cost` 는 비용 칼럼을 감춘다. `statusline` 서브커맨드로 상태줄에 물릴 수도 있다(베타).

| 장점 | 단점 |
| --- | --- |
| `npx` 한 줄, 설치·상주 프로세스 없음 | 실행 시점의 스냅샷이라 자동 누적은 직접 구성해야 함 |
| 일/주/월/세션/블록 집계 축이 가장 촘촘함 | 실시간 경고나 한도 예측은 제공하지 않음 |
| `--json` 출력으로 파이프라인 구성이 쉬움 | 비용은 토큰 수 기반 **추정치**이며 실제 청구 기록이 아님 |
| 클로드 외 다른 에이전트까지 통합 집계 | 에이전트가 로컬 로그를 제대로 남겨야만 정확함 |

## OTel + 그라파나

링크: [Claude Code 모니터링 공식 문서](https://code.claude.com/docs/en/monitoring-usage)

<!-- 이미지: ../assets/2026-07-31-토큰/4.png -->

앞의 세 도구가 "로그 파일을 나중에 읽는" 방식이라면, 이쪽은 클로드 코드가 **스스로 지표를 내보내게** 만드는 정공법이다. 클로드 코드는 OpenTelemetry 익스포터를 내장하고 있어, 환경변수 몇 개만 켜면 토큰·비용·활동 시간을 OTLP 나 프로메테우스로 흘려보낸다. 공식 문서가 명시하듯 개인 머신부터 클라우드 프로바이더 환경까지 유일하게 공통으로 동작하는 방법이기도 하다.

내보내는 주요 지표는 다음과 같다.

| 지표 | 설명 | 단위 |
| --- | --- | --- |
| `claude_code.token.usage` | 소비 토큰 수 | tokens |
| `claude_code.cost.usage` | 세션 비용 | USD |
| `claude_code.session.count` | 시작된 세션 수 | count |
| `claude_code.active_time.total` | 총 활동 시간 | s |
| `claude_code.lines_of_code.count` | 변경된 코드 라인 수 | count |

각 지표에는 `model`, `session.id`, `user.id`, `organization.id` 같은 속성이 붙는다. 모델별 토큰 소비를 나눠 보거나 팀 단위로 집계할 수 있는 근거가 여기에 있다.

가장 가벼운 구성은 프로메테우스가 직접 긁어가게 하는 것이다.

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=prometheus
# http://localhost:9464/metrics 로 노출된다
```

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'claude-code'
    static_configs:
      - targets: ['localhost:9464']
```

수집기(OTel Collector)를 거치는 일반적인 구성이라면 OTLP 로 보낸다.

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export OTEL_METRICS_EXPORTER=otlp
export OTEL_LOGS_EXPORTER=otlp
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4317
export OTEL_METRIC_EXPORT_INTERVAL=10000   # 기본 60000ms
```

매번 export 하기 번거롭다면 `~/.claude/settings.json` 에 박아두면 된다.

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://localhost:4317"
  }
}
```

그라파나에서는 `claude_code_*` 계열 지표를 쿼리해 패널을 구성하고, `model` / `session_id` / `user_id` 로 필터를 건다. 설정이 먹었는지 확인하려면 세션을 하나 시작한 뒤 백엔드에 `claude_code.session.count` 가 들어오는지 보면 되고, 익스포트가 실패하고 있다면 `claude --debug` 로 에러를 확인할 수 있다.

프롬프트 본문이나 툴 파라미터까지 남기는 `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_TOOL_DETAILS` 옵션도 있지만, 기본값이 꺼져 있는 데는 이유가 있으니 켜기 전에 무엇이 로그로 남는지 따져보는 편이 좋다.

| 장점 | 단점 |
| --- | --- |
| 로그 파싱이 아닌 공식 계측이라 신뢰도가 높음 | 수집기·시계열 DB·그라파나를 세워야 하는 초기 비용 |
| 준실시간 스트리밍, 무제한 보존 기간 | 개인 사용자 한 명에게는 명백한 과잉 설계 |
| 사용자·모델·조직 단위 속성으로 다차원 분석 | 대시보드는 직접 만들어야 함 (기성품 없음) |
| 클라우드 프로바이더 환경까지 유일하게 커버 | 프롬프트 로깅 옵션은 별도의 보안 판단이 필요 |

## 정리

| 도구 | 형태 | 설치 | 실시간 | 누적 이력 | 적합한 경우 |
| --- | --- | --- | --- | --- | --- |
| `/usage` | 내장 명령 | 불필요 | O | X | 지금 한도가 얼마나 남았는지 확인 |
| claude-monitor | 터미널 상주 | uv / pipx | O | O (`--warehouse`) | 한도 도달을 미리 경고받고 싶을 때 |
| claude-usage | 웹 대시보드 | brew / uv | X | O | 장기 추이를 차트로 훑어볼 때 |
| ccusage | CLI 스냅샷 | npx (불필요) | X | O (직접 적재) | 가볍게 집계하고 JSON 으로 기록할 때 |
| OTel + 그라파나 | 관측 스택 | 인프라 구성 | O | O | 팀 단위 계측, 장기 보존이 필요할 때 |

혼자 쓰는 입장에서의 결론은 이렇다. 평소에는 `/usage` 로 남은 한도만 확인하고, 실제 기록은 `ccusage daily --json` 을 크론에 걸어 파일로 쌓는 것으로 충분하다. 여기서 더 나아가 팀의 사용량을 관리해야 하는 시점이 오면 그때 OTel 을 세우면 된다.

한 가지 덧붙이면, 이 도구들이 보여주는 달러 금액은 대부분 토큰 수에 정가를 곱한 **추정치**다. 구독 플랜은 정액제이므로 그 숫자가 청구서가 되지는 않는다. 정확한 청구 내역은 [클로드 콘솔의 사용량 페이지](https://platform.claude.com/usage)에서 확인해야 한다. 그럼에도 이 숫자들이 쓸모 있는 이유는, 금액 자체보다 "무엇이 토큰을 먹고 있는가"라는 상대적인 비중을 알려주기 때문이다. 측정의 목적은 결국 거기에 있다.
