# 정규화(Nomalization)와 반정규화(Denomalization)

정규화와 반정규화는 수단을 일컫는 말이므로, 그 수단을 사용하는 이유, 목적을 알아야한다.

## 정규화

### 정규화: 이상 현상 (Anomaly)

정규화의 목적은 "무결성" 이다. 먼저 정규화가 되지 않은 아래와 같은 테이블을 보자.

| 학번  | 이름  | 학과   | 학과장 | 수강과목   | 학점 |
| ----- | ----- | ------ | ------ | ---------- | ---- |
| 20001 | 김철수 | 컴퓨터 | 이교수 | 자료구조   | A    |
| 20001 | 김철수 | 컴퓨터 | 이교수 | 데이터베이스 | B    |
| 20002 | 박영희 | 컴퓨터 | 이교수 | 자료구조   | A    |
| 20003 | 최민수 | 전자   | 정교수 | 회로이론   | C    |

하나의 테이블에 학생 정보, 학과 정보, 수강 정보가 뒤섞여 있다. 그 결과 같은 사실이 여러 행에 중복 저장된다. (예: `컴퓨터` 학과의 학과장이 `이교수`라는 사실이 세 번 반복된다.)

이렇게 중복이 존재하면 아래와 같은 **이상 현상 (Anomaly)** 이 발생한다.

- 갱신 이상 (Update): 
  - 학과장 이교수의 담당 학과 컴퓨터를 김철수에 대해서만 수정한다면, 데이터 불일치로 인한 "갱신 이상" 이 발생한다.
- 삽입 이상 (Insert) :
  - 새로운 학생을 등록하려 할 때, 학과 정보 혹은 학점이 없으면 등록할 수 없다.
- 삭제 이상 (Delete)
  - 학점 사실을 취소하려 할 때, 학생 정보 역시 제거된다.

  이 때 정규화는 **데이터를 주체별로 쪼개서 중복을 없애기 위한 구조화**이자 위와 같은 이상 현상을 방지하기 위한 수단이다. 

### 정규화의 대가: 조인(JOIN)

정규화는 데이터를 쪼개어 구조화하는 방법이므로, 조회 유즈케이스는 테이블 조인을 수반한다. **즉 관리는 편하지만, 읽기 성능 저하가 발생한다.**

## 반정규화 (Denormalization)

반정규화는 읽기 성능의 최적화를 위해, 테이블을 합치거나 기존 테이블의 컬럼을 추가하여 "일부러" 중복 허용하는 방식이다.

예를 들어, 정규화된 상태에서 `주문` 테이블은 상품을 `상품ID`로만 참조한다.

**주문 (정규화)**

| 주문ID | 주문일자   | 상품ID | 수량 |
| ------ | ---------- | ------ | ---- |
| 1001   | 2026-07-10 | P-01   | 2    |
| 1002   | 2026-07-18 | P-03   | 1    |

**상품**

| 상품ID | 상품명   | 단가   |
| ------ | -------- | ------ |
| P-01   | 키보드   | 30000  |
| P-03   | 모니터   | 200000 |

이 구조에서 "주문 목록에 상품명과 금액을 함께 보여주기"는 매번 `주문 JOIN 상품`을 요구한다. 주문 조회가 초당 수천 건씩 일어난다면 이 조인은 부담이 된다.

그래서 자주 함께 읽히는 `상품명`, `단가`를 `주문` 테이블에 **일부러 중복 저장**한다.

**주문 (반정규화)**

| 주문ID | 주문일자   | 상품ID | 상품명   | 단가   | 수량 | 총액   |
| ------ | ---------- | ------ | -------- | ------ | ---- | ------ |
| 1001   | 2026-07-10 | P-01   | 키보드   | 30000  | 2    | 60000  |
| 1002   | 2026-07-18 | P-03   | 모니터   | 200000 | 1    | 200000 |

이제 조인 없이 `주문` 테이블만 읽어도 필요한 정보가 나온다. `총액`처럼 계산 결과를 미리 저장해두는 것도 반정규화의 한 형태다.

즉 반정규화는 **"쓰기 비용·정합성 관리 부담"을 지불하고 "읽기 성능"을 사는** 트레이드오프다.

### 이력을 위한 반정규화

위의 예시에서 반정규화는 또 다른 역할을 수행한다. 바로 **그 시점의 사실을 박제하는 "스냅샷"** 이다.

앞서 `주문`에 복사해 둔 `단가`를 "중복이니 위험하다"고만 봤지만, 관점을 바꾸면 이야기가 달라진다. 상품의 가격은 시간이 지나면 바뀐다. 만약 `모니터`의 단가가 인상된다고 해보자.

**상품 (가격 인상 후)**

| 상품ID | 상품명   | 단가   |
| ------ | -------- | ------ |
| P-01   | 키보드   | 30000  |
| P-03   | 모니터   | 250000 |

이때 `주문` 테이블의 `단가`까지 `250000`으로 함께 갱신해버리면, **"2026-07-18에 20만 원에 샀다"는 과거의 사실이 사라진다.** 영수증·매출 정산·환불 금액이 전부 틀어진다.

그래서 이런 컬럼은 앞의 `상품명` 예시와 반대로 **일부러 동기화하지 않는다.** 주문 시점의 값을 그대로 고정해두면, 이후 원본이 어떻게 바뀌든 그 주문은 "당시의 진실"을 계속 증언한다.

| 주문ID | 주문일자   | 상품ID | 상품명   | 단가(주문 시점) | 수량 | 총액   |
| ------ | ---------- | ------ | -------- | --------------- | ---- | ------ |
| 1002   | 2026-07-18 | P-03   | 모니터   | 200000          | 1    | 200000 |

즉 여기서의 중복은 **정합성 관리 부담이 아니라, 오히려 이력 보존을 위한 의도된 설계**다. 같은 "중복 컬럼"이라도 최신값을 따라가야 하는 것(정합성 대상)과 그 시점에 고정돼야 하는 것(스냅샷)을 구분하는 것이 반정규화 설계의 핵심이다.

### 반정규화: 반정규화를 먼저 할 수 없다.

반정규화는 정규화된 모델을 바탕으로, 성능 문제가 발생했을 때 도입하는 수단이다. 다시말해 성능 **문제가 발생했을 때 전략적으로 정규화를 무너뜨리는 것이 반정규화**이다. 처음부터 중복을 허용한 설계는 잘못된 설계이다.

무결성이 중요한 시스템에서, RDBMS 테이블의 반정규화는 최후의 수단으로 여겨진다. 반정규화에 앞서 다음과 같은 수단을 검토해 볼 수 있다.

- 인덱스 튜닝
- View 테이블의 사용
- 캐시

(NoSQL 의 경우, 읽기 성능을 위해 설계 단계부터 데이터를 중복 저장하는 반정규화 방식을 지향한다.)

## 정규화와 반정규화 비교표

| 구분     | 정규화 (Normalization)                          | 반정규화 (Denormalization)                          |
| -------- | ----------------------------------------------- | --------------------------------------------------- |
| 목적     | 데이터 무결성 확보 (중복 제거)               | 읽기 성능 최적화 (조인 비용 절감)                 |
| 장점     | 이상 현상 방지, 저장 공간 절약, 쓰기·수정 용이  | 조회 속도 향상, 조인 감소, 이력 스냅샷 보존          |
| 단점     | 조인 증가로 읽기 성능 저하                  | 중복 발생 → 이상 현상 위험, 쓰기·정합성 관리 부담   |
| 적용 순서 | 먼저 (설계의 기본, Default)               | 나중에 (정규화된 모델에서 성능 문제 발생 시 전략적으로 도입, Optional) |

# 정규화를 통한 다양한 정규형

정규화를 통해, 아래와 같은 n차 정규형(Normal Form, NF)을 산출할 수 있다.

- UNF: 어떠한 정규형 조건도 만족하지 않는 형태
- 1NF: 모든 컬럼이 원자값(atomic) 임을 만족하는 형태
- 2NF: 1NF 조건을 만족하고, 부분 함수 종속을 제거한 형태
- 3NF: 2NF 조건을 만족하고, 이행 함수 종속을 제거한 형태
- BCNF: 3NF 조건을 만족하고, 모든 결정자가 후보키인 형태

## 제 1정규형 (1NF)

테이블의 모든 컬럼은 더 이상 조깨질 수 없는 값(Atomic Value)만 가져야한다.

## 제 2정규형와 3정규형 (2NF, 3NF)

2정규화는 "복합키의 일부부 에만 의존하는 컬럼을 분리해내는 것이다. 예를들어 (A, B) 복합키를 갖는 C 를 `(A, B) -> C` 로 표현하고, C 가 B 에 대해서만 의존(B만 알고 있으면 C임을 알 수 있는 경우)한다면, 이는 2정규형을 만족하지 않은 형태이다. 이 때 C는 복합키 (A, B)에 대해 부분(Particial) 함수 종속 상태이다.

3정규화는 위와 같은 의존 관계(A와 무관하며 B이면 C인 관계)에서 키가 A이고, A이면 B인 관계가 존재하며(`A -> B -> C`), 이 컬럼들이 같은 테이블에 존재하는 경우, C 는 일반 컬럼에 의존하고 B 는 키에 의존하므로 3정규화를 만족하지 않은 형태이다. 이 때 C 는 A에 따른 이행(Transitive) 함수 종속 상태이다.

### 제 2정규형: 예시

제 2정규형을 만족하려면 복합키와 컬럼들 사이에서 부분 함수 종속 관계를 제거하여 완전 함수 종속 관계들로 바꾸어야한다.

- ex. PK (주문번호, **상품ID**) -> **상품명**
- to. PK (주문번호) -> 상품ID -> 상품명

### 제 3정규형: 예시

제 3정규형을 만족하려면 이행 함수 종속을 제거한다.

- ex. (주문번호) -> 상품ID -> 상품명
- to. PK (주문번호) -> 상품ID / PK (상품ID) -> 상품명

### 정리: 1~3NF

| 단계 | 키워드                  | 이를 위한 행동             |
| ---- | ----------------------- | ---------------- |
| 1NF  | 원자값 (Atomic)         | 리스트 분리      |
| 2NF  | 부분 함수 종속 없음         | 복합키 쪼개기    |
| 3NF  | 이행 함수 종속 없음     | 건너건너 종속 분리 |
