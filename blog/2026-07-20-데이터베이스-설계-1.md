## 단일 DB, 단일 테이블 구조의 한계

단일 DB, 단일 테이블 구조에서는 아래와 같은 한계 상황을 만날 수 있다.

- I/O 병목 심화: 데이터 증가에 따라 인덱스 깊이가 증가하고, 디스크 접근 비용이 상승
- 동시성 충돌 증가: 트랜잭션 경합과 락 대기 시간이 증가
- 운영 비용 폭증: 백업, 복구, 배포 시간이 기하급수적으로 증가
- 물리적 한계 도달: CPU, 메모리, 디스크 확장의 한계에 직면

## 파티셔닝(Partitioning)

단일 DB 서버 내부에서 하나의 거대한 테이블을 여러 파티션(저장 단위)으로 나누어 저장하는 행위를 파티셔닝이라 한다. 이 때, 개발자는 하나의 테이블처럼 데이터에 접근하지만 DB 내부에서는 여러 파티션으로 분리되어 저장될 수 있다. 이는 대개 DB 엔진 수준에서 관리하는 영역이다.

### 파티셔닝의 종류

- 범위(Range): 날짜나 숫자 범위를 기준으로 분할 (ex. 월별 로그, 연도별 데이터)
- 목록(List): 특정 값의 목록을 기준으로 분할 (ex. 지역코드-서울, 부산)
- 해시(Hash): 해시 함수를 통해 데이터를 균등 분산. 값 쏠림을 방지한다.
- 복합(Composite): 두 개 이상의 파티션 전략을 조합한다.

### 파티셔닝의 활용 

다음과 같은 유즈케이스에서 활용할 수 있다.

- 로그 테이블: 시간 기준으로 지속 누적되는 대용량 테이블
- 날짜 기반 데이터: 최신 데이터 조회 성능이 중요한 경우
- 주기적 정리가 필요한 테이블: 오래된 데이터를 통째로 정리해야하는 경우 (Drop Partition)

즉, 파티셔닝은 DB 내부 최적화 전략이다.

## 샤딩(Sharding)

데이터를 서로 다른 물리적 서버(인스턴스)들에 분산 저장함을 말한다. 각 서버를 샤드(Shard)라 부르며 수평 확장의 핵심 기술이다.

대개 DB 엔진에서 관리하는 파티셔닝과 달리, 샤딩은 일반적으로 애플리케이션(또는 미들웨어)에서 샤드 키 기반 라우팅을 통해 쿼리 대상 서버를 결정한다.

### 샤딩의 활용

- 대규모 트래픽/데이터 규모: 단일 DB 한계를 넘었을 경우
- 글로벌 서비스: 지역별 데이터를 물리적으로 분산해야하는 경우(데이터 로컬리티 확보)
- 스케일 업의 한계: 단일 서버 사양을 높여 대응하는 것의 한계에 도달한 경우

샤딩을 도입할 때, 조인 연산이 어려워지므로 데이터의 모델링이 중요해진다. 단일 DB 한계를 극복하기 위한 최후의 수단에 가깝다.

## 파티셔닝 vs 샤딩

| 구분 | 파티셔닝(Partitioning) | 샤딩(Sharding) |
| --- | --- | --- |
| 서버 | 단일 DB 서버 내에서 분할 | 여러 물리 서버(인스턴스)에 분산 |
| 관리 주체 | DB 엔진 수준에서 관리 | 애플리케이션(또는 미들웨어)에서 관리 |
| SQL 수정 여부 | 불필요 (하나의 테이블처럼 접근) | 필요 (샤드 키 기반 라우팅) |
| 확장성 방향 | 수직 확장(Scale-up) 위주 | 수평 확장(Scale-out) |

## 스케일 아웃: 리플리케이션과 샤딩의 차이

### 리플리케이션(Replication)

원본 데이터를 여러 서버에 복제하는 것을 말한다. 대부분 Full Copy 형태로 복제하나, 일부는 필터링하여 복제할 수 있다.

- 목적: Read Scale-out 과 고가용성(High Availability)
- 도구: MySQL Binlog, PostgreSQL Streaming, AWS Aurora

#### 리플리케이션의 장단점

리플리케이션은 다음과 같은 장점과 단점을 갖는다.

- 장점
  - 구현이 비교적 쉬움
  - 읽기 부하를 확실히 분산
  - 장애 발생 시 승격을 통한 Failover
- 단점
  - 기본 구조에서 쓰기 병목은 해결 불가
    - 모든 쓰기 작업이 Primary 노드에 집중
  - 데이터 복제로 전체 저장 용량 증가
  - 복제 지연(Replication Lag) 발생 가능

### 샤딩(Sharding)

앞선 설명과 같이 샤딩은 데이터를 수평 분할하여 분산 저장하는 방식이다.

- 목적: 쓰기 성능 확장 및 전체 저장 용량 확장
- 방식: Hash(ID % N), Range(날짜), List/Composite

#### 샤딩의 장단점

샤딩은 다음과 같은 장단점을 갖는다.

- 장점
  - 쓰기 성능 선형적 확장 가능
  - 개별 DB의 부하/용량 감소
  - 수 TB 이상의 거대 데이터셋 처리
- 단점
  - 조인(JOIN) 거의 불가능
  - Hot Shard (데이터 쏠림) 위험
  - 재샤딩(Resharding)의 고통

### 리플리케이션 vs 샤딩

| 구분 | 리플리케이션(Replication) | 샤딩(Sharding) |
| --- | --- | --- |
| 목적 | 읽기 확장(Read Scale-out)과 고가용성 | 쓰기 확장(Write Scale-out)과 용량 확장 |
| 데이터 형태 | 동일 데이터 복제 (Full Copy) | 데이터 수평 분할 (서로 다른 데이터) |
| 쓰기 병목 | 해결 불가 (Primary에 집중) | 해결 가능 (선형적 확장) |
| 저장 용량 | 복제본만큼 증가 | 샤드별로 분산·감소 |
| 조인(JOIN) | 자유롭게 가능 | 거의 불가능 |
| 구현 복잡도 | 상대적으로 낮음 | 높음 (라우팅, 재샤딩 부담) |
| 언제? | 읽기가 많을 때 | 용량이 부족할 때 (마지막 카드) |

차이를 기술하였으나, 상호배타적인 전략은 아니다. 샤딩을 사용한다면 실무에서는 일반적으로 리플리케이션을 혼용한다.

CockroachDB 와 TiDB 처럼 자동 샤딩 + 복제를 지원하고, MySQL 과 호환되는 내장된 분산 SQL 을 지원하는 솔루션도 존재한다.
