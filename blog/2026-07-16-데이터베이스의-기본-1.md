## 잠금(Lock)과 관련한 용어의 혼동

개발자는 Race Condition, 혹은 상호배제 문제를 해결하기 위해 Lock 기법을 사용한다. 이에 따라 우리는 데드락, 기아 상태와 같은 여러 문제를 맞닥뜨린다. 재밌는 사실은 데드락, 기아와 같은 컴퓨터 공학 존재 이전에 존재했고, 컴퓨터 공학이나 개발 실무에서 이러한 단어들을 차용하는 것, 그리고 한글로 번역되는 과정에서 묘한 혼동이 존재한다는 사실을 발견했다는 것이다.

"락에 걸렸다", "락을 획득했다" 와 같은 대표적인 혼용은 각각 "데드락에 걸려 무언가 블록되었다", "동시성 환경에서 뮤텍스 락을 획득했다" 와 같이 풀어 쓸 수 있을 것이다. 물론, 우리는 고맥락 사회를 사는 한국인이므로 실무에 큰 지장이 없을 혼동이다. 그러나 개념 자체를 정교히 하고, 내 스스로의 사고를 정교히 다듬는 것은 또 다른 배움이자 즐거움이다. 하여, 이 글에서는 락과 트랜젝션의 관련한 기본적인 개념들을 다시한번 돌아본다.

### 동시성 시스템에서의 진행조건(Progress Conditions)위반

이 글에서는 Lock 에 의한 진행없음, 블록킹, 지연 등의 문제를 진행조건위반이라 표현하겠다. 이는 동시성 시스템에서 한 프로세스를 주체로 보았을 때, 발생하는 어떠한 문제 집합이 프로세스가 자원의 획득과 반환을 진행하기 위한 조건에 위반함을 표현한 것이다. (널리 쓰이는 용어가 있으면 참 좋겠다.)

여러 트랜젝션이 존재하는 시스템에서 한정된 자원에 대해 락을 활용할 때, 아래와 같은 진행조건위반을 만날 수 있다.

| 용어 | 프로세스 상태 | 진행 여부 | 전형적인 상황 |
| --- | --- | --- | --- |
| 데드락 (Deadlock) | 블록됨 — 상태 변화 없음 | 관련 프로세스 모두 진행 없음 | 두 트랜젝션이 서로가 쥔 락을 순환 대기 |
| 라이브락 (Livelock) | 실행 중 — 상태는 계속 변함 | 진행 없음 | 충돌 회피를 위해 서로 계속 양보/재시도만 반복 |
| 기아 (Starvation) | 대기 중 | 시스템은 진행하나 특정 프로세스만 진행 없음 | 우선순위가 낮은 트랜젝션이 락 획득에서 계속 밀려남 |
| 우선순위 역전 (Priority inversion) | 대기 중 | 지연됨 | 낮은 우선순위 프로세스가 쥔 락을 높은 우선순위 프로세스가 기다림 |

### 진행조건(Progress Conditions)위반의 예시

#### 데드락(Deadlock)

```python
# 트랜젝션 T1          # 트랜젝션 T2
lock(A)                lock(B)
lock(B)  # B 대기...    lock(A)  # A 대기...
```

T1은 A를 쥔 채 B를 기다리고, T2는 B를 쥔 채 A를 기다린다. 서로가 서로의 반환을 기다리는 **순환 대기**가 형성되어, 둘 다 블록된 채 영원히 멈춘다.

**해결**: 순환 대기를 끊는 것이 핵심이다.

- 모든 트랜젝션이 자원을 **동일한 순서**로 획득하도록 강제한다 (A → B 순서 통일)
- 락 획득에 **타임아웃**을 걸어 실패 시 보유 자원을 반환하고 재시도한다
- DBMS처럼 대기 그래프에서 사이클을 **감지**하면 한쪽(victim)을 롤백시킨다

#### 라이브락(Livelock)

```python
# 트랜젝션 T1                    # 트랜젝션 T2
while True:                     while True:
    lock(A)                         lock(B)
    if not try_lock(B):             if not try_lock(A):
        unlock(A)  # 양보 후 재시도       unlock(B)  # 양보 후 재시도
```

데드락을 피하려고 "실패하면 양보하고 재시도"를 넣었지만, 두 트랜젝션이 **같은 타이밍에** 양보와 재시도를 반복하면 상태는 계속 변하는데 진행은 없다. 블록되지 않고 CPU를 소모하기 때문에 데드락 감지에도 걸리지 않는다.

여기서 "양보"는 한 사례일 뿐이다. PostgreSQL SSI 와 같은 낙관적/적렬화 격리에서 트랜젝션 충돌 시 abort 후 재시도하는데, 경합이 심할 경우 재시도된 트랜젝션들이 서로를 다시 abort 시키는 재시도 폭풍, 즉 라이브락이 발생할 수도 있다. 낙관적 락에서의 라이브락 발생도 다른 사례로 얘기해볼 수 있다.

**해결**: 재시도의 대칭성을 깨는 것이 핵심이다.

- 재시도 전 **랜덤 백오프**(무작위 대기)를 넣어 타이밍을 어긋나게 한다
- 재시도 횟수를 제한하고, 초과 시 상위 계층에서 실패 처리한다
- 애초에 자원 획득 순서를 통일해 경합 자체를 없앤다

#### 기아(Starvation)

```python
# 읽기 요청이 끊임없이 유입되는 상황
acquire_read(R)   # 읽기 락은 서로 공유 가능 → 계속 통과
acquire_read(R)
acquire_write(R)  # 쓰기 락은 배타적 → 읽기가 끊길 때까지 무한 대기
acquire_read(R)   # 새 읽기가 또 끼어듦...
```

읽기 우선 정책의 공유 락에서, 읽기 요청이 끊이지 않으면 쓰기 트랜젝션은 **영원히 순서가 오지 않는다**. 시스템 전체는 멀쩡히 진행되고 있으므로 데드락보다 발견하기 어렵다.

**해결**: 공정성(fairness)을 보장하는 것이 핵심이다.

- **공정 락**(FIFO 큐)을 사용해 요청 순서대로 락을 부여한다
- **에이징(aging)**: 오래 대기한 요청의 우선순위를 점진적으로 올린다
- 쓰기 요청이 대기 중이면 새 읽기 요청의 진입을 막는다 (쓰기 우선 정책)

#### 우선순위 역전(Priority inversion)

```python
low.lock(A)        # 낮은 우선순위 L이 락 획득
high.lock(A)       # 높은 우선순위 H가 대기 → L이 끝나야 함
mid.run()          # 중간 우선순위 M이 L을 선점하고 계속 실행
                   # 결과: H가 사실상 M보다 낮은 우선순위로 동작
```

높은 우선순위 H는 L이 락을 반환해야 진행할 수 있는데, 락과 무관한 중간 우선순위 M이 L을 선점해버리면 H는 M이 끝날 때까지 기다리는 꼴이 된다. 우선순위가 사실상 뒤집힌 것이다. 1997년 화성 탐사선 패스파인더의 반복적인 시스템 리셋 원인으로 유명하다.

**해결**: 락을 쥔 쪽의 우선순위를 일시적으로 올리는 것이 핵심이다.

- **우선순위 상속(priority inheritance)**: 락 보유자 L의 우선순위를 대기자 H 수준으로 임시 상승시켜 M의 선점을 막는다
- **우선순위 상한(priority ceiling)**: 락 자체에 상한 우선순위를 정해두고, 락 획득 시 그 수준으로 실행한다

### 데드락(Deadlock) 에 대한 추가적인 개념

#### Coffman Conditions

Coffman 등이 1971년 논문 *System Deadlocks* 에서 정리한, 데드락이 발생하기 위한 4가지 **필요조건**이다. 넷 중 하나라도 성립하지 않으면 데드락은 발생할 수 없다.

| 조건 | 의미 |
| --- | --- |
| 상호배제 (Mutual exclusion) | 자원은 한 번에 하나의 프로세스만 사용할 수 있다 |
| 점유와 대기 (Hold and wait) | 자원을 쥔 채로 다른 자원을 기다린다 |
| 비선점 (No preemption) | 쥐고 있는 자원을 강제로 빼앗을 수 없다 |
| 순환 대기 (Circular wait) | 프로세스들의 자원 대기 관계가 사이클을 이룬다 |

이 조건들이 유용한 이유는, 데드락 예방 전략이 곧 **"이 중 하나를 무너뜨리는 것"** 으로 정리되기 때문이다.

- 상호배제 제거 → 락 없는 자료구조(lock-free), MVCC처럼 읽기와 쓰기가 서로를 막지 않는 설계
- 점유와 대기 제거 → 필요한 자원을 한 번에 모두 획득하고, 하나라도 실패하면 전부 반환
- 비선점 제거 → 타임아웃, DBMS의 victim 롤백처럼 자원을 강제로 회수
- 순환 대기 제거 → 자원에 전역 순서를 부여하고 항상 그 순서로만 획득

앞서 데드락 해결책으로 나열했던 기법들이 사실 각각 어느 조건을 공략하는지 대응되는 것을 볼 수 있다.

#### 식사하는 철학자 문제

Dijkstra가 1965년에 고안한 고전 문제로, 데드락과 기아를 한 장면에 담고 있다. 원탁에 철학자 5명이 앉아 있고, 각자의 사이에 포크가 하나씩(총 5개) 놓여 있다. 식사를 하려면 양옆의 포크 **2개**가 모두 필요하다.

```python
# 철학자 i 의 행동
while True:
    think()
    lock(fork[i])            # 왼쪽 포크
    lock(fork[(i + 1) % 5])  # 오른쪽 포크
    eat()
    unlock(fork[(i + 1) % 5])
    unlock(fork[i])
```

모든 철학자가 동시에 왼쪽 포크를 집으면, 전원이 오른쪽 포크를 기다리며 영원히 멈춘다. Coffman 조건 4가지가 모두 성립하는 순간이다 — 포크는 한 명만 쓸 수 있고(상호배제), 왼쪽을 쥔 채 오른쪽을 기다리며(점유와 대기), 남의 포크를 빼앗을 수 없고(비선점), 대기 관계가 원탁을 따라 사이클을 이룬다(순환 대기).

**해결**: 역시 Coffman 조건 중 하나를 깨는 것으로 정리된다.

- **자원 순서화**: 포크에 번호를 매기고 항상 낮은 번호부터 집게 한다. 마지막 철학자만 집는 순서가 반대가 되어 사이클이 끊긴다 (순환 대기 제거)
- **동시 입장 제한**: 식탁에 최대 4명만 앉게 한다(세마포어). 누군가는 반드시 포크 2개를 집을 수 있다 (순환 대기 제거)
- **중재자(waiter)**: 포크를 집으려면 중재자의 허락을 받는다. 양쪽 포크가 모두 가능할 때만 허락한다 (점유와 대기 제거)

이 문제가 고전인 이유는 단순해 보이는 규칙에서 데드락이 필연적으로 도출되고, 해결책마다 트레이드오프가 드러나기 때문이다. 예컨대 중재자 방식은 안전하지만 중재자가 병목이자 단일 장애점이 된다 — 분산 락 매니저를 두는 실무 설계와 정확히 같은 고민이다.

### DB 동시성 제어: 성능과 안전 사이

#### 비관적 락(Pessimistic Lock)

충돌이 **일어날 것이라 가정**하고, 데이터를 읽는 시점부터 락을 걸어 다른 트랜젝션의 접근을 막는 방식이다.

```sql
SELECT * FROM account WHERE id = 1 FOR UPDATE;  -- 배타 락 획득
UPDATE account SET balance = balance - 100 WHERE id = 1;
COMMIT;  -- 커밋 시점에 락 반환
```

대표적으로 `SELECT ... FOR UPDATE`(배타 락), `FOR SHARE`(공유 락)가 있으며, DBMS 내부의 2단계 잠금(2PL)도 같은 철학이다.

**언제 쓰나**: 충돌이 잦은 데이터(재고 차감, 계좌 이체, 좌석 예약)나, 충돌 시 롤백 비용이 커서 재시도가 부담스러운 긴 트랜젝션에 적합하다.

**낙관 대비 장점**: 충돌이 아예 발생하지 않도록 차단하므로 **재시도 로직이 필요 없다**. 경합이 심해도 처리량이 예측 가능하게 유지된다 — 낙관적 락이라면 재시도 폭풍으로 이어질 상황에서도 순서대로 처리된다. 대신 데드락의 위험은 이쪽이 짊어진다.

#### 낙관적 락(Optimistic Lock)

충돌이 **드물 것이라 가정**하고, 락 없이 작업한 뒤 커밋(저장) 시점에 충돌 여부를 검사하는 방식이다. 엄밀히는 락이 아니라 **충돌 검출**이다.

```sql
SELECT id, balance, version FROM account WHERE id = 1;  -- version = 3
UPDATE account SET balance = 900, version = 4
 WHERE id = 1 AND version = 3;  -- 그 사이 누가 고쳤다면 0건 갱신 → 재시도
```

대표적으로 버전 컬럼(JPA `@Version`), CAS 연산, 그리고 DBMS의 MVCC 기반 직렬화 검증이 이 계열이다.

**언제 쓰나**: 읽기가 압도적으로 많고 쓰기 충돌이 드문 데이터(게시글 수정, 설정 값)나, 락을 유지할 수 없는 구간(사용자가 화면을 보고 있는 동안의 갱신 충돌 방지)에 적합하다.

**비관 대비 장점**: 락을 쥐고 기다리는 구간이 없어 **경합이 적을 때 처리량이 높고, 데드락이 원천적으로 없다**(락을 쥐지 않으니 순환 대기가 성립하지 않는다). 대신 충돌 시 재시도는 애플리케이션의 몫이며, 경합이 심하면 앞서 본 라이브락(재시도 폭풍)으로 번질 수 있다.

### 트랜젝션

#### 트랜젝션의 ACID

트랜젝션은 "여러 작업을 하나의 논리적 단위로 묶은 것"이고, ACID는 그 단위가 지켜야 할 4가지 성질이다.

| 성질 | 의미 | 주로 책임지는 것 |
| --- | --- | --- |
| 원자성 (Atomicity) | 전부 성공하거나 전부 실패한다 — 중간 상태는 없다 | 롤백, undo 로그 |
| 일관성 (Consistency) | 트랜젝션 전후로 데이터의 제약과 불변식이 유지된다 | 제약 조건 + 애플리케이션 로직 |
| 격리성 (Isolation) | 동시에 실행되는 트랜젝션이 서로의 중간 상태를 보지 못한다 | 락, MVCC |
| 지속성 (Durability) | 커밋된 결과는 장애가 나도 사라지지 않는다 | WAL(redo 로그), fsync |

넷 중 성격이 다른 하나는 일관성이다. 나머지 셋은 DBMS가 메커니즘으로 보장하지만, 일관성은 "무엇이 올바른 상태인가"의 정의 자체가 애플리케이션의 몫이기 때문이다 (계좌 잔고가 음수가 되면 안 된다는 규칙은 DB가 알 수 없다).

그리고 이 글의 주제와 직결되는 것이 **격리성**이다. 격리성을 완벽히 보장하는 것(직렬화)은 비싸기 때문에, DBMS는 격리를 단계별로 흥정할 수 있게 해두었다 — 그것이 격리수준이다.

#### 트랜젝션의 격리수준

SQL 표준은 "격리가 깨질 때 나타나는 이상 현상(anomaly)"을 기준으로 4단계를 정의한다. 아래로 갈수록 격리가 강해지고, 동시성(성능)은 낮아진다.

| 격리수준 | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

각 이상 현상은 "다른 트랜젝션의 무엇이 보이는가"로 구분된다.

- **Dirty Read**: 커밋되지 않은 데이터를 읽음 — 상대가 롤백하면 존재한 적 없는 값을 읽은 것이 된다
- **Non-repeatable Read**: 같은 행을 두 번 읽었는데 값이 다름 — 그 사이 다른 트랜젝션이 수정 후 커밋
- **Phantom Read**: 같은 조건으로 두 번 조회했는데 행 개수가 다름 — 그 사이 다른 트랜젝션이 삽입/삭제

주의할 점은, 이 표는 표준의 정의일 뿐 실제 DBMS의 동작과는 차이가 있다는 것이다.

- **PostgreSQL**의 기본값은 READ COMMITTED이며, REPEATABLE READ는 MVCC 스냅숏 덕에 표준과 달리 **팬텀도 발생하지 않는다** (스냅숏 격리)
- **MySQL(InnoDB)**의 기본값은 REPEATABLE READ이며, 넥스트키 락으로 팬텀을 상당 부분 막는다
- **SERIALIZABLE**의 구현은 앞의 두 진영이 그대로 이어진다 — 잠금 기반(2PL)은 비관적 락의 철학이고, PostgreSQL의 SSI는 충돌을 감지해 abort시키는 낙관적 방식이다. SSI에서 경합이 심하면 재시도 폭풍(라이브락)이 가능하다고 했던 것이 바로 이 지점이다

결국 격리수준이란 "이상 현상을 얼마나 감수하고 동시성을 살 것인가"라는 눈금이고, 그 눈금을 구현하는 재료가 이 글에서 다룬 락과 MVCC다.

### Redo, Undo

ACID 표에서 원자성은 undo 로그가, 지속성은 redo 로그(WAL)가 책임진다고 했다. 두 로그는 방향이 정반대다.

| 로그 | 기록하는 것 | 언제 쓰이나 | 책임지는 성질 |
| --- | --- | --- | --- |
| Undo | 변경 **이전** 값 | 롤백, 장애 복구 시 미커밋 변경 취소, MVCC의 과거 버전 재구성 | 원자성 (+ 격리성) |
| Redo | 변경 **이후** 값 | 장애 복구 시 커밋된 변경 재적용 | 지속성 |

두 로그가 모두 필요한 이유는, DBMS가 성능을 위해 디스크 반영 시점을 트랜젝션의 생명주기와 **분리**해두었기 때문이다. 데이터 페이지는 메모리(버퍼 풀)에서 수정되고 디스크에는 나중에 내려간다. 그래서 장애 시점에는 두 가지 어긋남이 공존할 수 있다.

- **커밋했는데 디스크에 없다** → redo 로그를 재생해 다시 적용한다 (roll forward)
- **커밋 안 했는데 디스크에 있다** → undo 로그로 되돌린다 (roll back)

이때 "데이터 페이지보다 로그를 먼저 디스크에 쓴다"는 규칙이 **WAL(Write-Ahead Logging)** 이다. 커밋 시점에는 로그만 fsync하면 되므로, 무작위 위치의 데이터 페이지 쓰기를 순차적인 로그 쓰기로 바꿔 성능과 지속성을 동시에 얻는다. 장애 복구는 "redo로 장애 직전 상태를 재현한 뒤, 미커밋 트랜젝션을 undo로 걷어내는" 순서로 진행된다 (ARIES 알고리즘의 골격).

한 가지 흥미로운 지점은 undo가 복구만이 아니라 **MVCC의 재료**이기도 하다는 것이다. InnoDB는 다른 트랜젝션이 수정 중인 행을 읽을 때 undo 로그를 거슬러 올라가 스냅숏 시점의 과거 버전을 재구성한다. 앞서 "일반 SELECT는 락 없이 읽는다"고 했던 것이 가능한 이유다. 반면 PostgreSQL은 undo 로그가 아예 없다 — 과거 버전 행을 테이블 안에 그대로 남겨두는 방식(그래서 VACUUM이 필요하다)으로, 같은 MVCC를 정반대 재료로 구현한 사례다.

## 마무리

정리하다보니 "락에 걸렸다"는 한 마디에서 출발한 글이 꽤 멀리까지 왔다. 정리하면 이렇다.

락은 상호배제를 위한 **도구**이고, 데드락·라이브락·기아·우선순위 역전은 그 도구가 만들어내는 **진행조건위반**들이다. 데드락의 "lock"은 뮤텍스의 "lock"과 어원부터 다른 단어인데, 같은 분야에서 우연히 공존하며 혼동을 만든다. Coffman 조건은 데드락이라는 문제를 "네 개의 필요조건 중 하나를 깨면 된다"는 공략 가능한 구조로 바꿔주었고, 식사하는 철학자 문제는 그 공략법들의 트레이드오프를 한 장면에 담아냈다.

비관적 락과 낙관적 락은 "충돌을 어떻게 가정하는가"라는 태도의 차이이며, 각자의 대가도 대칭적이다 — 비관은 데드락을, 낙관은 라이브락(재시도 폭풍)을 짊어진다. 격리수준은 이 비용을 단계별로 흥정하는 눈금이고, 그 눈금의 구현 재료가 락과 MVCC다. 그리고 그 아래에는 undo와 redo라는 두 로그가 원자성과 지속성을, 나아가 MVCC 자체를 떠받치고 있다.

돌아보면 이 글에서 다룬 개념들은 결국 하나의 질문을 변주한 것이다 — **"동시에 일어나는 일들 사이에서, 무엇을 얼마나 포기하고 무엇을 지킬 것인가."** 락이라는 단어의 혼용을 정리하는 것에서 시작했지만(ㅎㅎ;), 용어를 정교히 하는 일은 결국 그 뒤에 있는 트레이드오프의 구조를 정교히 이해하는 일이었다. 다음에 누군가 "락 걸렸어요"라고 말한다면, 그것이 어떤 락이고 어떤 대가의 결과인지 한 겹 더 들여다볼 수 있을 것이다.
