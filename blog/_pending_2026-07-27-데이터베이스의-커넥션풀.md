## 기본 개요

DB 커넥션의 생성은 성능적 비용이 많이 드는 작업이므로, 풀링(Pooling)을 통해 자원(커넥션)을 관리한다.

## 커넥션 풀 사이즈(Connection Pool Size)

어플리케이션에서, 커넥션 풀링을 제공하는 라이브러리들은 각기 다른 이름으로 아래 세 가지 파라미터를 노출한다.

| 파라미터 | 의미 |
| --- | --- |
| 최대 커넥션 수 | 풀이 가질 수 있는 커넥션의 상한 |
| 최소 커넥션 수 | 유휴 상태에서도 유지하는 커넥션 수 |
| 초기 생성 커넥션 수 | 풀을 만드는 시점에 미리 맺어둘 커넥션 수 |

(구현체 중 대부분은 지연 생성 방식이다. 이 경우 실질적인 초기 커넥션 수는 최소 커넥션 수가 결정한다.)

### DB 관점: 알려진 공식을 통한 상한 예측

커넥션 풀 사이즈의 초기 설정은 [PostgreSQL Wiki](https://wiki.postgresql.org/wiki/Number_Of_Database_Connections)에서 유래하여, [HikariCP 문서](https://github.com/brettwooldridge/HikariCP/wiki/About-Pool-Sizing)가 인용해 유명해진 아래 공식을 출발점으로 잡을 수 있다. 이는 경험적 데이터를 바탕으로 최적 활성 커넥션 수를 표현한 식으로, 그 식은 아래와 같다.

```
// DB 기준
connections = (core_count × 2) + effective_spindle_count
```

| 항목 | 의미 | 실무에서의 해석 |
| --- | --- | --- |
| `core_count` | **DB 서버**의 코어 수 | 앱 인스턴스 스펙과 무관하다 |
| `effective_spindle_count` | 디스크가 동시에 처리 가능한 I/O 개수 (≈ HDD 스핀들 수) | SSD·클라우드에서는 무의미 |

이 때, 결과 값 `connections` 는 DB에 붙은 "active connections" 커넥션의 총량이다. 따라서 인스턴스의 풀은 아래와 같은 식을 참조할 수 있다.

- DB max_connections : `(DB 서버 코어 수 × 2) + 여유분`
- `Σ(instance max_connections) < DB max_connections − 운영/모니터링 예약분`
